# 设备售后协同智能体——项目概述与整体架构

---

## 第1章 项目背景

### 1.1 为什么要做这套系统

设备售后与运维每天都在处理大量重复又零散的对话：

- "这台设备还在保修期吗？" "帮我查下维修到哪了"
- "H3C LA2608 怎么配置业务 VLAN？" "万用表读数不准怎么办？"
- "你好" "帮我报修" "算了先不修了"

如果靠人工坐席，要养一个大团队；如果用传统关键词机器人，遇到稍微复杂的问法就答非所问——尤其是「型号 + 故障 + 是否在保 + 要不要建单」这类多轮任务。

在大模型逐渐成熟之后，"用 LLM 理解用户意图 + 用代码执行具体动作" 成为了一种新的工程范式。本项目要做的就是这样一套系统：

**让用户用自然语言描述设备问题，由系统判断这句话该交给谁处理，再用工程化的方式把事情做完（查手册、查保修、建工单、必要时转人工）。**

### 1.2 传统系统和 AI 系统的差异

在写第一行代码之前，先建立一个认知。本项目的写法和大家熟悉的 CRUD 项目有几个关键的不同。

| 维度 | 传统 CRUD 系统 | 本项目（AI 驱动） |
| --- | --- | --- |
| 输入 | 结构化参数 | 用户的自然语言 |
| 路由 | 由 URL / 方法名决定 | 由 LLM 现场推断 |
| 输出 | 严格 JSON | 自然语言 + 结构化对象 |
| 响应时间 | 毫秒级 | 秒级（LLM 推理 1~5 秒） |
| 不确定性 | 几乎没有 | LLM 可能返回幻觉、漂移、违反 schema |
| 状态 | 通常无状态 | 多轮对话强状态（任务可中断/恢复） |

这套差异决定了我们整个项目要围绕一个核心命题来设计：

> **如何用工程化的方式驯服 LLM 的不确定性，保证业务结果稳定可控？**

本项目后续讲到的三个关键设计——**结构化输出 + 校验白名单 + 澄清兜底**、**LLM 路由 + YAML 流程编排双引擎**、**会话状态与任务栈管理**——本质上都是在回答这个命题。

在售后场景里还要多打一根钉子：

> **LLM 只负责理解和规划；建单、取消等写操作必须经代码校验 + 用户确认后，才允许调用业务中台。**

## 第2章 系统能力

本系统支持三类能力，对应三条处理轨道。

### 2.1 任务流程（Task）

任务流程指那些**步骤明确、可以按步骤推进**的售后业务，例如保修查询、工单创建、维修进度、转人工。

| 流程名称 | 触发场景 | 大致步骤 |
| --- | --- | --- |
| 保修查询 | "DEV-2026-0001 还在保修吗？" | 收集设备编号 → 调用保修接口 → 回复结果 |
| 工单创建 | "我的 LA2608 连不上 AC，帮我报修" | 收集设备编号/故障/已试步骤 → **用户确认** → 创建工单 |
| 维修进度 | "我那个单子修到哪了？" | 收集工单号 → 调用维修进度接口 → 回复轨迹 |
| 转人工 | "转人工" / 连续失败 / 高风险 | 创建人工接入记录 → 回复已转接 |

我们用 YAML 文件描述这类流程，下面是工单创建的简化定义：

```yaml
create_service_ticket:
  name: 售后工单创建
  description: 收集设备编号、故障描述与已试步骤，经用户确认后创建售后工单。
  steps:
    - id: start
      type: start
      next: ask_device_id

    - id: ask_device_id
      type: collect
      slot_name: device_id
      response:
        text: "请提供设备编号，例如 DEV-2026-0001。"
      next: ask_problem

    - id: ask_problem
      type: collect
      slot_name: problem_desc
      response:
        text: "请描述故障现象，以及已经尝试过的处理步骤。"
      next: confirm_create

    - id: confirm_create
      type: confirm
      response:
        text: "将为设备 {{ slots.device_id }} 创建工单，故障：{{ slots.problem_desc }}。是否确认？"
      next: ticket_created

    - id: ticket_created
      type: action
      action: action_create_service_ticket
      args:
        device_id: "{{ slots.device_id }}"
        problem_desc: "{{ slots.problem_desc }}"
        confirmed: true
      next: end

    - id: end
      type: end
      next: []
```

一个流程由若干 step 组成，本项目支持的 step 类型：

- `start`：流程起点
- `collect`：收集某个槽位（slot），例如设备编号、故障描述
- `confirm`：高风险写操作前的用户确认（**没有确认不许执行 action**）
- `action`：执行动作并生成回复（回复、调用中台 HTTP 接口）
- `end`：流程结束

对应的流程图：

```text
        ┌─────────┐
        │  start  │
        └────┬────┘
             ▼
     ┌───────────────┐
     │ collect       │
     │ device_id     │
     └───────┬───────┘
             ▼
     ┌───────────────┐
     │ collect       │
     │ problem_desc  │
     └───────┬───────┘
             ▼
     ┌───────────────┐
     │ confirm       │  ← 用户拒绝则取消/改槽
     └───────┬───────┘
             ▼
     ┌───────────────┐
     │ action        │  ← create_service_ticket(confirmed=true)
     └───────┬───────┘
             ▼
        ┌─────────┐
        │   end   │
        └─────────┘
```

交互示例：

```text
用户：我的 LA2608 连不上无线控制器，帮我报修
客服：请提供设备编号，例如 DEV-2026-0001。
用户：DEV-2026-0001
客服：请描述故障现象，以及已经尝试过的处理步骤。
用户：AP 一直无法上线，已经重启过，也检查过网线
客服：将为设备 DEV-2026-0001 创建工单，故障：AP 无法上线…是否确认？
用户：确认
客服：工单 TKT-2026-000004 已创建，状态为「已提交，等待受理」。
```

**这种写法的关键在于**：业务的步骤、转移、提示语都不写在代码里，而是写在 YAML 里。代码里只有一个通用的"流程执行器"按定义往前推。增加一个新流程不需要改代码，只需要加一份 YAML。  
**写操作的安全闸门（confirm 步骤 + confirmed=true）也在流程里强制体现**，避免模型擅自建单。

### 2.2 信息检索（Knowledge）

很多用户问题不需要走"流程"，只是想问一句"这个型号怎么配 VLAN？""保修多久？"。我们用知识检索的方式来回答。

本项目把知识问题分成几类，每一类对应不同的信息源：

| 知识意图 | 示例问题 | 信息源 |
| --- | --- | --- |
| 手册配置/操作 | "H3C LA2608 怎么配置业务 VLAN？" | 设备手册 RAG（shopkeeper_brain） |
| 故障排查引导 | "万用表读数漂移怎么办？" | 手册 RAG + 排查话术 |
| 设备档案咨询 | "这台是什么型号、什么时候买的？" | 设备中台 API |
| 保修政策咨询 | "保修一般多久？过保怎么收费？" | FAQ |
| 售后政策咨询 | "寄修运费谁出？" | FAQ |
| 通用设备问题 | "电池能用多久？" | FAQ + RAG |

信息源的选择会根据问题类型自动切换。例如实时档案走设备中台 API，手册步骤走 RAG 并带引用。

交互示例：

```text
用户：LA2608 怎么配置业务 VLAN？
客服：请先在 AC 上创建业务 VLAN，再在 AP 的下行口放行该 VLAN…（引用：H3C LA2608 用户手册 · 配置指南）

用户：这台设备还在保修期吗？
客服：设备 DEV-2026-0001（H3C LA2608）保修截止 2027-02-15，目前在保，剩余约 XXX 天。
```

### 2.3 闲聊（Chitchat）

剩下那些既不属于明确任务、也不适合走知识检索的输入，例如"你好""你挺聪明的"，统一走闲聊轨道兜底。

```text
用户：你好
客服：你好，这里是设备售后助手。我可以帮你查手册、查保修、创建维修工单，或转接人工。
```

闲聊的作用主要是让对话体验更自然，避免用户的轻量输入被直接拒答。

### 2.4 三条轨道的关系

```text
                 用户自然语言
                       │
                       ▼
              ┌─────────────────┐
              │   TurnPlanner   │  LLM 是路由器（单选）
              │  结构化 TurnPlan │
              └────────┬────────┘
           ┌───────────┼───────────┐
           ▼           ▼           ▼
      ┌─────────┐ ┌──────────┐ ┌──────────┐
      │  Task   │ │Knowledge │ │ Chitchat │
      │ 任务流程 │ │ 信息检索  │ │  闲聊    │
      │YAML+Action│ │RAG/API/FAQ│ │  兜底   │
      └─────────┘ └──────────┘ └──────────┘
```

三条轨道是互斥的——任何一句话只会走其中一条。判断走哪一条的工作交给 LLM（`TurnPlanner`），这就是后面我们会反复强调的"LLM 是路由器"。  
若模型一次输出多个轨道，**不直接执行**，而是澄清：「请先确认你想查询维修方法，还是创建售后工单？」

## 第3章 项目开发环境

### 3.1 仓库与服务划分

整套项目由独立服务组成（可多仓库，也可 monorepo）：

```text
device_agent/
├── atgui_agent/                      ← 本工作区（中台 + 前端 + Agent 网关）
│   ├── device-service-backend/       ← 设备维修业务中台（已具备）
│   ├── device-service-frontend/      ← 售后工作台前端（已具备）
│   └── agent-gateway/                ← AI Agent 后端（主战场，待迭代）
│
└── （独立项目）
    └── shopkeeper_brain/             ← 设备手册 RAG（E:\AAA message get\shopkeeper_brain）
```

为什么要拆开？简短回答如下，更深入的权衡放到后面的课讲：

| 服务 | 角色 | 类似你熟悉的 |
| --- | --- | --- |
| `agent-gateway`（Agent 后端） | 对话与 LLM 调用、任务编排 | 业务网关 / BFF |
| `device-service-backend` | 设备、保修、工单、转人工等确定性业务 | 真实企业里被消费的中台 |
| `shopkeeper_brain` | 手册解析、索引、召回、引用 | 知识中台 / RAG 服务 |
| `device-service-frontend` | 聊天 + 设备/工单对象工作台 | Web UI |

**核心理念**：

1. AI Agent **不直接读**业务数据库，只以"业务系统消费者"身份调用中台 HTTP 接口。  
2. Agent **不复制** RAG 内部实现（BGE-M3 / Milvus / RRF / Rerank），只封装 `search_manual` 一类工具。  
3. 业务中台稳定后，AI 应用可独立迭代；AI 出问题也不会反向污染业务数据。

```text
RAG 项目：如何解析、索引、召回和引用知识？
Agent 项目：什么时候查知识、什么时候查保修、什么时候创建工单？
```

### 3.2 组件交互全景

```text
                    ┌────────────────────┐
                    │ Web 工作台 :5173   │
                    │ 对话 + 设备/工单    │
                    └─────────┬──────────┘
                              │  Vite 代理
              /api/*          │         /device/*
                    ┌─────────▼──────────┐
                    │ Agent 网关 :8100   │
                    │ 对话编排 + LLM     │
                    └─────────┬──────────┘
                              │ Tool 调用
                    ┌─────────▼──────────┐
                    │ 设备维修中台:18082 │
                    │ 保修/工单/转人工    │
                    └───┬────────────┬───┘
                        │            │ /manual/search
                        ▼            ▼
                 ┌────────────┐  ┌──────────────────┐
                 │ MySQL      │  │ shopkeeper_brain │
                 │ 业务+状态  │  │ RAG :8001        │
                 └────────────┘  └──────────────────┘
```

几个关键点：

- 前端用 Vite 反向代理统一到 5173，按路径前缀分流到 Agent（`/api`）或中台（`/device`），不在前端硬编码后端 IP
- Agent 要存「对话状态」，独占 `customer_service.dialogue_states` 等表；中台存设备/工单业务表
- LLM 调用走 OpenAI 兼容协议，通过统一客户端接入
- 手册问答经中台 `POST /manual/search` 转到 RAG `POST /query`，失败可降级 stub

### 3.3 Agent 后端 agent-gateway

这是后续每一节课都会回到的核心服务。它的主要职责：

- 接收用户消息（文本或设备/工单对象）
- 读取和保存对话状态（含任务中断/恢复）
- 用 LLM 推断用户意图，路由到任务、知识或闲聊轨道
- 校验计划与工具权限，必要时要求用户确认
- 调用设备维修中台 / 经中台调用 RAG
- 生成自然语言回复（可带结构化对象与引用）

主要技术栈：

| 技术 | 作用 |
| --- | --- |
| FastAPI | 提供 HTTP 接口 |
| Uvicorn | ASGI 服务器 |
| LangChain + langchain-openai | LLM 编排，prompt → model → parser 流水线 |
| Pydantic / pydantic-settings | 数据校验与配置加载 |
| Jinja2 | Prompt 模板渲染 |
| SQLAlchemy + aiomysql | 异步访问 MySQL（对话状态） |
| httpx | 异步调用中台 HTTP 接口 |

Agent 后端建议**全异步**（`async/await`）。原因很直接——LLM 调用是高延迟 I/O（单次 1~5 秒），同步阻塞会把并发打满。

### 3.4 设备维修中台 device-service-backend

标准 CRUD 微服务，扮演"被 AI 消费的业务中台"。核心接口：

| 接口 | 作用 | Agent 工具 |
| --- | --- | --- |
| `GET /customers/{id}/devices` | 客户设备列表 | （前端侧边栏） |
| `GET /customers/{id}/tickets` | 客户工单列表 | （前端侧边栏） |
| `GET /devices/{device_id}` | 设备档案 | `get_device_profile` |
| `GET /devices/{device_id}/warranty` | 保修查询 | `check_warranty` |
| `GET /devices/{device_id}/history` | 设备历史 | `get_device_history` |
| `GET /tickets/{ticket_id}/status` | 工单状态 | `get_ticket_status` |
| `GET /tickets/{ticket_id}/repair` | 维修/寄送进度 | `get_repair_progress` |
| `POST /devices/{device_id}/tickets` | 创建工单（需确认） | `create_service_ticket` |
| `PATCH /tickets/{ticket_id}` | 更新工单 | `update_service_ticket` |
| `POST /tickets/{ticket_id}/cancel` | 取消工单（需确认） | `cancel_service_ticket` |
| `POST /transfers` | 转人工 | `transfer_to_human` |
| `POST /manual/search` | 手册检索（代理 RAG） | `search_manual` |
| `GET /tools` | 工具注册表 | ToolRegistry 映射 |

技术栈：同步 FastAPI + PyMySQL + SQLAlchemy。这类 CRUD 单次耗时短（&lt; 50ms），同步代码更易写易读。

> 异步不是万能药。**异步的真正价值是高延迟 I/O 场景**（如 LLM、RAG），对短耗时的 CRUD 反而是负担。

**安全约定**：`create_service_ticket` / `cancel_service_ticket` 等写接口必须 `confirmed=true`，否则 400——这是中台侧的硬闸门，不单靠 Agent 自觉。

### 3.5 手册 RAG shopkeeper_brain

面向设备手册的垂直 RAG：PDF 导入 → 切分/清洗 → 向量化入库 → 混合检索 + Rerank → 带结构化引用的答案。

Agent **只调用**其查询接口（经中台代理）：

```http
POST http://127.0.0.1:8001/query
{ "query": "H3C LA2608 怎么配置业务 VLAN？", "is_stream": false }
```

返回 `answer` + `sources[]`（file_title / title / snippet / score…），由中台映射为 `citations` 回给 Agent。  
**简历与文档中不要在 Agent 项目重复展开 BGE-M3、Milvus、RRF、Rerank 的内部实现。**

### 3.6 前端 device-service-frontend

教学与联调用的可视化工作台，两个区域：

- 左侧聊天区：发送文本消息、查看回复、查看历史
- 右侧对象区：当前客户的**设备**与**工单**卡片，可一键作为消息发出

右侧的"对象消息"机制很重要——用户点设备卡片说"这台帮我报修"，比纯文本信息量大得多。后端可直接把 `device_id` 填入流程槽位，不用再追问"请问设备编号是？"

## 第4章 项目架构

### 4.1 分层结构

Agent 后端的代码组织遵循清晰分层（与电商小二同构，语义换成设备售后）：

| 层 | 主要职责 | 关键模块 |
| --- | --- | --- |
| API 层 | 接收 HTTP 请求，组织请求与响应 | `agent_gateway/api/` |
| Service 层 | 一次对话事务：加载状态 → 调引擎 → 保存状态 | `agent_gateway/service/` |
| Engine 层 | 顶层调度，决定走哪条处理轨道 | `agent_gateway/engine/` |
| Plan 层 | LLM 本轮规划、校验、澄清兜底 | `agent_gateway/plan/` `clarify/` |
| Task 层 | 推进固定任务流，执行 Action | `agent_gateway/task/` |
| Knowledge 层 | 手册/档案/政策检索并生成回复 | `agent_gateway/knowledge/` |
| Chitchat 层 | 闲聊兜底 | `agent_gateway/chitchat/` |
| Domain 层 | 消息、上下文、对话状态领域模型 | `agent_gateway/domain/` |
| Repository 层 | DialogueState 持久化 | `agent_gateway/repository/` |
| Infrastructure 层 | LLM、HTTP 客户端、数据库 | `agent_gateway/infrastructure/` |

整体调用关系：

```text
HTTP → API → DialogueService
                │ ① load DialogueState
                ▼
           DialogueEngine
                │ TurnPlanner → Validator → (Clarify?)
                ├──────────────┬──────────────┐
                ▼              ▼              ▼

                │              │

         ActionRunner         │
                │              ▼
                └──────► device-service-backend
                              │
                         shopkeeper_brain
                │
                ▼ ② save DialogueState
```

### 4.4 一条消息的完整处理流程

```text
用户消息
   │
   ▼
① Service 加载 DialogueState（含 active_task / paused_tasks / focused_device）
   │
   ▼
② Engine：TurnPlanner 生成 TurnPlan
   │
   ▼
③ TurnPlanValidator（route 白名单 / 槽位 / 设备编号 / 工具权限）
   │
   ├─ 失败 → ClarifyResponder 反问
   │
   ▼
④ 按 route 进入 Task / Knowledge / Chitchat
   │     Task：FlowExecutor 推进；写 Action 前若无确认 → 停在 WAITING_CONFIRMATION
   │     Knowledge：search_manual 或 check_warranty 等
   │
   ▼
⑤ 组装 BotMessage（文本 + 可选对象/引用/建议 chips）
   │
   ▼
⑥ Service 保存 DialogueState → 返回前端
```

注意两个边界：

- **① 加载状态和 ⑥ 保存状态是 Service 层的事务边界**——持久化集中在这两步  
- 中间引擎处理**不直接做状态 I/O**，变更都落在 DialogueState 内存对象上  

这种 "Service 管 I/O，Engine 管计算" 的设计来自 DDD 的**事务脚本 + 充血模型**，引擎可单测、可换存储。

**任务中断示例**：

```text
当前任务：创建工单（COLLECTING_SLOTS）
用户突然问：这台还在保修吗？
  → 诊断任务 → paused_tasks
  → 保修查询 → task（当前）
  → 保修完成 → 恢复原创建工单任务
```

### 4.5 设计要点回顾

第一节课不需要看懂每个细节，但请建立下面几个判断：

1. **三条轨道分离**——任务、知识、闲聊各走各的代码路径，互不污染  
2. **LLM 路由 + 白名单校验 + 澄清兜底**——永远不"裸用" LLM 输出  
3. **YAML 描述流程，代码执行流程**——可枚举业务交给状态机，不让模型直接写库  
4. **写操作双闸门**——流程 `confirm` + 中台 `confirmed=true`，缺一不可  
5. **DialogueState 集中状态，Engine 集中计算**——I/O 在边缘，计算在中心  
6. **业务与知识隔离**——Agent 只消费中台与 RAG 的 HTTP 接口，不直连其库、不复制 RAG 内部实现  

这六点是本项目要反复打的钉子，后续每讲一个模块都会回到其中一两条。

### 4.6 与 smart-cs-multi-agent 的结合

多智能体不是「所有问题都必须过一遍 Supervisor」。本项目采用**轻量 Supervisor + 按需协作**：

`	ext
Supervisor（编排器，agent_gateway 的 engine）
├── Knowledge Agent      手册问答（knowledge 轨道）
├── Device Diagnosis     故障分析（复杂诊断时串联）
├── Warranty Agent       保修/售后条件查询
├── Work Order Agent     工单创建（service 轨道）
└── Escalation Agent     转人工
`

**普通任务走单道**：

`	ext
Supervisor → 单一领域 Agent → 确定性工具（中台 HTTP）
`

**复杂诊断才串联**：

`	ext
Supervisor
  → Knowledge Agent 查手册
  → Device Diagnosis 分析故障
  → Warranty Agent 查售后条件
  → Work Order Agent 创建工单
`

第一版先做单一编排器 + 领域工具（本仓库现状），把 Supervisor 拆分留到评测稳定之后。

**三轨道路由必须单选**（knowledge / service / chitchat）。模型若同时输出多条轨道，不直接执行，改为澄清：

`	ext
请先确认你想查询维修方法，还是创建售后工单？
`

**分层记忆**（吸收 smart-cs 的记忆设计，对应本项目的 DialogueState）：

| 层级 | 内容 | 落点 |
| --- | --- | --- |
| 短期 | 当前消息、active task / current_context | DialogueState（内存 + JSON 一行） |
| 会话 | 当前设备、历史工单、用户确认结果 | turns + focused_object + task.slots |
| 长期 | 设备常见故障、用户偏好、人工反馈 | 后续扩展（RAG / 画像表） |

**观测**：后续接 OpenTelemetry，记录路由结果、校验结果、工具耗时/失败原因、LLM token、最终任务状态。
